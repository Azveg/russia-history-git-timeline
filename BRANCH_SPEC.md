# Спецификация модульных веток Git-таймлайна (`BRANCH_SPEC.md`)

Этот документ задаёт **статические правила**: архитектуру, JSON-формат, механизмы синхронизации, стратегии пакетной/последовательной генерации и **системный промпт для ИИ-моделей**.
Актуальный список уже добавленных веток, активных тегов `syncTags`, ID правителей и ID событий вынесен в автоматически обновляемый файл [`BRANCH_CATALOG.md`](./BRANCH_CATALOG.md) — при работе с ИИ передавайте **оба файла** (`BRANCH_SPEC.md` + `BRANCH_CATALOG.md`).

---

## 1. Принцип Plug-and-Play и полная изоляция

Проект использует модульную систему загрузки данных из директории `public/data/`:

1. **Автообнаружение при сборке и в dev-режиме:**
   - Любой `.json`-файл, добавленный в `public/data/` (включая вложенные подпапки, например `public/data/campaigns/ww2-fronts.json`), автоматически обнаруживается Vite-плагином и попадает в виртуальный индекс `./data/modules.index.json`.
   - Редактировать `sync.manifest.json` или TypeScript-код для подключения новой ветки **не требуется**.
   - Файл `modules.index.json` генерируется автоматически — создавать его вручную не нужно.

2. **Безопасное удаление и полная изоляция ошибок:**
   - Удаление любого файла ветки (включая опциональные модули и даже базовые файлы) **не нарушает работу сайта**: удалённые файлы исключаются из загрузки.
   - **Висячие связи (`linksTo` / `crossLinks`):** если целевое событие (`targetId`, `from` или `to`) находится в удалённом или ещё не созданном файле, движок молча пропускает отсутствующую связь без ошибок UI.
   - **Битые файлы или узлы:** некорректный JSON или отдельный узел без обязательных полей пропускаются изолированно; остальные файлы и события продолжают отображаться.
   - **Осиротевшие события (`ev.task`):** если узел ссылается на `task`, объявление которого удалено, движок автоматически синтезирует для него отдельную тематическую дорожку справа от оси времени, никогда не смешивая его с веткой правителей (`MAIN_RULERS`).
   - **Динамический диапазон лет:** ось времени автоматически расширяет границы (`minYear–maxYear`), если добавлены модули ранее 1686 г. (например, `ERA_1`–`ERA_4`) или после 2000 г.
   - **Временное отключение без удаления файла:** добавьте `"enabled": false` в корень JSON-файла, и модуль будет полностью исключён из рендера.

## 2. Формат файла ветки (`BranchFile`)

Каждый модульный файл в `public/data/` представляет собой JSON-объект со следующей структурой:

```json
{
  "$schema": "https://git-timeline.schema.org/v2/branch.json",
  "fileId": "unique_file_id",
  "path": "data/my_branch.json",
  "version": "1.0.0",
  "enabled": true,
  "branch": { ... },
  "nodes": [ ... ],
  "crossLinks": [ ... ]
}
```

### Поля верхнего уровня

| Поле | Тип | Обяз. | Описание |
| :--- | :--- | :---: | :--- |
| `$schema` | `string` | Нет | Рекомендуется `"https://git-timeline.schema.org/v2/branch.json"` |
| `fileId` | `string` | **Да** | Уникальный строковый идентификатор файла (латиница, `snake_case` или `kebab-case`) |
| `path` | `string` | **Да** | Относительный путь внутри `public/`, например `"data/science.json"` |
| `version` | `string` | Нет | Версия схемы файла, например `"1.0.0"` |
| `enabled` | `boolean` | Нет | По умолчанию `true`. Значение `false` отключает файл без удаления |
| `branch` | `BranchDefinition` | * | Объявление одной ветки (используйте `branch` **или** `branches`) |
| `branches` | `BranchDefinition[]` | * | Массив веток (для группы кампании и её фронтов в одном файле) |
| `nodes` | `TimelineNode[]` | **Да** | Массив исторических событий/процессов (хронологически упорядоченный) |
| `crossLinks` | `CrossLink[]` | Нет | Дополнительные явные связи на уровне файла |

> *Для корректного отображения и фильтрации файл должен объявлять `branch` или `branches`. Исключение: файл-дополнение к уже существующей ветке из другого файла.*

### Описание ветки (`BranchDefinition`)

| Поле | Тип | Обяз. | Описание |
| :--- | :--- | :---: | :--- |
| `id` | `string` | **Да** | Уникальный ID ветки в `UPPER_SNAKE_CASE` (напр. `"SCIENCE_TECH"`, `"WW2_WEST_FRONT"`). На него ссылается `node.task` |
| `gitName` | `string` | **Да** | Git-имя дорожки в интерфейсе (напр. `"feat/science"`, `"war/ww2-arctic"`). Не используйте `time/main` и `rulers/reigns` |
| `label` | `string` | **Да** | Человекочитаемое название ветки в меню и на матрице перекрытий |
| `short` | `string` | **Да** | Короткая метка для шапки графа (до ~16 символов, напр. `"science"`, `"ww2/arctic"`) |
| `description` | `string` | **Да** | Краткое пояснение тематики ветки |
| `color` | `string` | **Да** | Цвет линии и узлов в формате HEX (`"#a78bfa"`). Не используйте `#cbd5e1` (ось времени) и `#f59e0b` (правители) |
| `badgeClass` | `string` | **Да** | Tailwind-классы бейджа (напр. `"bg-violet-500/15 text-violet-300 border-violet-500/40"`) |
| `isMilitary` | `boolean` | **Да** | `true` для военных кампаний/фронтов, `false` для гражданских/тематических веток |
| `category` | `string` | Нет | Одна из: `"military"`, `"economy"`, `"world"`, `"other"` (для правителей зарезервировано `"rulers"`) |
| `sourceFile` | `string` | Нет | Путь файла-источника (совпадает с `path`) |
| `isGroup` | `boolean` | Нет | `true` — родительская ветка-контейнер для объединения фронтов/подветок в одну линию |
| `parentBranchId` | `string` | Нет | `id` родительской группы (можно ссылаться как на группу в этом файле, так и в другом файле, напр. `"WAR_ALL"`) |
| `defaultEnabled` | `boolean` | Нет | Информационный флаг в схеме; на старте приложения по умолчанию активны только `TIME_AXIS` (`time/main`) и `MAIN_RULERS`, а все тематические/военные ветки включаются пользователем в меню «Ветки» |
| `defaultCollapsedOnTimeline` | `boolean` | Нет | `true` — при наличии дочерних веток они по умолчанию слиты в одну общую линию с кнопкой раскрытия |

### Описание узла события (`TimelineNode`)

| Поле | Тип | Обяз. | Описание |
| :--- | :--- | :---: | :--- |
| `id` | `string` | **Да** | Глобально уникальный идентификатор в формате `<год>-<kebab-slug>` (напр. `"1961-gagarin-flight"`) |
| `startYear` | `number` | **Да** | Целый год начала события (`<= endYear`) |
| `endYear` | `number` | **Да** | Целый год окончания события (`>= startYear`). Для точечного события `endYear === startYear` |
| `startDate` | `string` | Нет | Уточнённая дата начала: `"YYYY"`, `"YYYY-MM"` или `"YYYY-MM-DD"` (нужна для детализации в узких окнах `<= 12` и `<= 2` лет) |
| `endDate` | `string` | Нет | Уточнённая дата окончания: `"YYYY"`, `"YYYY-MM"` или `"YYYY-MM-DD"` |
| `isAtomic` | `boolean` | Нет | `true` для точечного одномоментного коммита (отображается ромбом на ветке без цикла ответвление→слияние) |
| `period` | `string` | **Да** | Отображаемая строка периода (напр. `"1941–1945"`, `"1961 (апрель)"`, `"1861"`) |
| `title` | `string` | **Да** | Краткий ёмкий заголовок события (до ~90 символов) |
| `subtitle` | `string` | **Да** | Подзаголовок-резюме (1 фраза, суть и результат) |
| `details` | `string` | **Да** | Развёрнутое историческое описание для модальной карточки (`git show`) |
| `task` | `string` | **Да** | `id` листовой (не `isGroup`) ветки, к которой принадлежит событие |
| `region` | `string` | **Да** | Географический регион или театр действий |
| `type` | `string` | **Да** | Тип события (напр. `"Научный прорыв"`, `"Мирный трактат"`, `"Наступательная операция"`, `"Экономическая реформа"`) |
| `subEvents` | `SubEvent[]` | Нет | Массив вложенных этапов/сражений: `[{ "title": "...", "text": "..." }]` |
| `linksTo` | `InlineNodeLink[]` | Нет | Прямые исходящие связи к другим событиям (внутри файла или к другим файлам, включая `"references"` на любое расстояние лет) |
| `campaignId` | `string` | Нет | Идентификатор кампании (работает аналогично `syncTags` для синхронизации в окне ±3 года) |
| `syncTags` | `string[]` | Нет | Теги синхронной эпохи в строгом `kebab-case` (авто-связь в окне ±3 года) |
| `referenceTags` | `string[]` | Нет | Внеоконные теги отложенных/культурных отсылок (книги, фильмы, исследования спустя любое число лет, напр. `["event-1914-ww1", "ww1"]`) |

## 3. Архитектура иерархий веток и фронтов

Граф поддерживает произвольную древовидную иерархию веток через пару полей `isGroup` + `parentBranchId`:

1. **Самостоятельная иерархия кампании (в одном файле):**
   - Объявите в массиве `branches` родительскую ветку-группу с `"isGroup": true` (и при желании `"defaultCollapsedOnTimeline": true`, чтобы на старте все фронты были слиты в одну компактную линию, а пользователь мог раскрыть их по клику).
   - Объявите дочерние ветки фронтов/направлений с `"parentBranchId": "<ID_ГРУППЫ>"`.
   - Все события (`nodes`) привязывайте через `task` **только к дочерним веткам** (привязка узла к ветке с `isGroup: true` запрещена).

2. **Подключение новой подветки в уже существующую группу:**
   - В файле новой ветки просто укажите `"parentBranchId": "WAR_ALL"` (или ID другой существующей группы).
   - Если родительская группа присутствует — ветка автоматически встроится в её дерево в меню и сможет сворачиваться вместе с ней. Если родительский файл будет удалён — дочерняя ветка всё равно отобразится как самостоятельная верхнеуровневая линия.

3. **Многоуровневая вложенность:**
   - Допускается цепочка `Группа -> Подгруппа -> Фронт`. Движок определяет самого верхнего свёрнутого предка на таймлайне и корректно сливает в него дочерние рельсы.
   - Циклические ссылки (`A -> B -> A` или `A -> A`) строго запрещены.

## 4. Механизмы синхронизации (с осью, прошлыми и будущими ветками)

### 4.1. Синхронизация с центральной осью времени (`time/main`) и правителями
- **Не добавляйте ручных привязок к правителям или эпохам в узлы!** Движок сам вычисляет пересечения `startYear..endYear` с `rulers.json` (если он загружен) и распределяет узлы по периодам `ERA_1–ERA_11`.
- Для точного позиционирования при масштабировании окна (`<= 12 лет` — месяцы, `<= 2 лет` — дни) заполняйте `startDate` и `endDate` в ISO-формате (`YYYY-MM-DD` или `YYYY-MM`). Если точный день неизвестен — используйте `YYYY-MM` или не указывайте `startDate`/`endDate`.
- Если в одном году/ветке идут два и более длительных процесса параллельно, граф автоматически разведёт их в параллельные под-нити (`subLanes`).

### 4.2. Трёхуровневая межветочная синхронизация (включая отложенные на десятилетия отсылки)

Чтобы новая ветка автоматически строила связи как с синхронными событиями, так и с книгами/работами, написанными спустя 50–200 лет, используются три слоя:

#### Слой 1 — Явные связи (`linksTo` внутри узла или `crossLinks` в файле)
Работают **на любом расстоянии лет** (даже если разница 50, 100 или 300 лет):
```json
"linksTo": [
  {
    "targetId": "1914-ww1",
    "type": "references",
    "label": "Документальный или художественный цикл о Первой мировой войне (спустя 50+ лет)"
  }
]
```
Допустимые значения `type`:
- `"triggers"` — исходное событие запустило/спровоцировало целевое (`Причина → Следствие`);
- `"enables"` — исходное событие создало условия/возможность для целевого;
- `"sync_context"` — события развиваются в общем историческом контексте;
- `"references"` / `"about_event"` / `"inspired_by"` — культурная, литературная, научная или мемуарная отсылка к другому событию (даже написанная спустя десятилетия). В карточке исторического события такие связи попадают в отдельный фиолетовый раздел **«Отражение в книгах, произведениях и отложенных событиях»** с расчётом разницы лет (`+50 л. спустя`).

> **Важно:** если указанный `targetId` будет удалён пользователем или ещё не создан, сайт не упадёт — связь просто не отобразится до появления целевого узла.

#### Слой 2 — Синхронная авто-связь по эпохе (`syncTags` и `campaignId`, окно ±3 года)
Движок автоматически находит все пары событий **из разных веток** (`a.task !== b.task`), у которых есть общий нормализованный тег в `syncTags`/`campaignId` и интервалы пересекаются или отстоят **не более чем на 3 года**:
`Math.max(a.startYear, b.startYear) <= Math.min(a.endYear, b.endYear) + 3`.

#### Слой 3 — Внеоконная авто-связь без ограничения лет (`referenceTags` и `event-<node.id>`)
Используется, когда более поздний узел (книга, фильм, памятник, диссертация, исследование, написанные через 5, 50 или 200 лет) относится к прошлому событию или историческому персонажу:
1. Укажите на позднем узле (например, книге 1968 года) массив `"referenceTags"`:
   - либо тег конкретного события **`"event-<node.id>"`** (например, `"event-1914-ww1"` — срабатывает **автоматически** даже без наличия тега в исходном файле события!),
   - либо канонический тег кампании/персонажа (например, `"ww1"` или `"person-tolstoy-leo"`), который объявлен в `syncTags` целевого события или биографии.
2. Движок связывает узел с первичным событием **на любой дистанции лет** (ограничение в 3 года отключено) и отображает книгу прямо в разделе **«Отражение в книгах, произведениях и отложенных событиях»** карточки события (и в обратной карточке книги).
3. При этом книги между собой не создают лишнего «шума» из попарных связей — каждая книга целенаправленно связывается со своим первоисточником/событием.

### 4.3. Единый стандарт генерации тегов для каждого события, персонажа и темы

Чтобы разные ИИ-модели и последовательные запуски всегда генерировали **идентичные теги без разночтений**, соблюдайте строгий синтаксис:
- **Алфавит и формат:** строго строчная латиница, цифры и дефис (`^[a-z0-9]+(?:-[a-z0-9]+)*$`). Кириллица, пробелы, подчёркивания и заглавные буквы запрещены.
- **Транслитерация имён:** стандартная латинская транслитерация (`а→a, б→b, в→v, г→g, д→d, е/ё→e, ж→zh, з→z, и/й→i, к→k, л→l, м→m, н→n, о→o, п→p, р→r, с→s, т→t, у→u, ф→f, х→kh, ц→ts, ч→ch, ш→sh, щ→shch, э→e, ю→yu, я→ya`, мягкий/твёрдый знак опускаются).

| Сущность | Единый шаблон тега | Куда ставить | Примеры |
| :--- | :--- | :--- | :--- |
| **Историческое событие** | `event-<node.id>` | На само событие (опц. в `syncTags`), на отсылки к нему (в `referenceTags`) | `event-1914-ww1`, `event-1812-patriotic-war`, `event-1861-reform-emancipation` |
| **Крупная кампания из каталога** | `<campaign-slug>` (как в `BRANCH_CATALOG.md`) | В `syncTags` событий эпохи или `referenceTags` поздних книг | `northern-war`, `napoleonic`, `ww1`, `ww2` |
| **Персонаж / автор / деятель** | `person-<surname>-<name>` (без отчества) | В `syncTags` на узел биографии, в `syncTags`/`referenceTags` на его работы | `person-pushkin-alexander`, `person-tolstoy-leo`, `person-dostoevsky-fyodor`, `person-peter-1` |
| **Сквозная тема / течение** | `topic-<slug>` | На ключевые опорные узлы темы | `topic-silver-age`, `topic-space-race`, `topic-cold-war` |

> **Запрещено** придумывать произвольные синонимы (`tolstoy`, `l-tolstoy`, `writer-tolstoy`, `leo-tolstoy`) — всегда используйте единый формат `person-<surname>-<name>` или `event-<node.id>`.

## 5. Строгие ограничения и правила качества

1. **Идентификаторы `id`:**
   - Узлы: только латиница, цифры и дефис (`<год>-<тема>-<slug>`), глобально уникальны во всех файлах `public/data/`.
   - Ветки: только латиница, цифры и подчёркивание (`UPPER_SNAKE_CASE`), глобально уникальны.
   - Запрещённые ID веток: `TIME_AXIS`, `MAIN_RULERS`.
2. **Валидность дат и хронология:**
   - `startYear` и `endYear` — целые числа; всегда `startYear <= endYear`.
   - `startDate` и `endDate` (если заданы) — строго `YYYY`, `YYYY-MM` или `YYYY-MM-DD` (год в `startDate` должен соответствовать `startYear`, в `endDate` — `endYear`).
   - Узлы внутри массива `nodes` должны идти в хронологическом порядке (по возрастанию `startYear`).
3. **Запрет привязки событий к группе:**
   - Если ветка имеет `"isGroup": true`, ни один узел не должен иметь `"task": "<ID_ЭТОЙ_ГРУППЫ>"`.
4. **Без дублирования правлений:**
   - Не добавляйте в тематическую ветку узлы смены царей/генсеков/президентов — эта роль закреплена за `rulers.json`.
5. **Самодостаточность текстов:**
   - Заголовок (`title`), подзаголовок (`subtitle`) и описание (`details`) пишутся на грамотном русском языке, кратко, фактологически точно и без HTML/Markdown-разметки.
6. **Проверка валидатором:**
   - После создания или изменения файла обязательно запускайте `npm run validate:branches`.

## 6. Динамический каталог проекта (`BRANCH_CATALOG.md`) и макро-периоды

### 6.1. Почему каталог вынесен в отдельный файл
Чтобы правила создания модулей оставались стабильными и не раздувались вручную после каждого коммита, все меняющиеся реестры вынесены в автогенерируемый файл [`BRANCH_CATALOG.md`](./BRANCH_CATALOG.md):
- актуальная сводка по базе и фактический диапазон оси времени (`minYear–maxYear`);
- полный список текущих веток (`id`, `gitName`, `parentBranchId`, цвета, число событий, файл);
- все активные теги `syncTags` и `campaignId` с диапазонами лет, участвующими ветками и ID событий;
- актуальный перечень `id` правителей (`rulers.json`) и полный каталог `node.id` для явных связей `linksTo`.

> **Перед генерацией новой ветки** модель (или разработчик) должна сверяться с [`BRANCH_CATALOG.md`](./BRANCH_CATALOG.md), чтобы переиспользовать существующие `syncTags`, не дублировать `id` и ставить точные `linksTo.targetId`. После добавления или удаления JSON-файлов `BRANCH_CATALOG.md` автоматически синхронизируется командой `npm run sync:catalog` и через GitHub Actions.

### 6.2. Канонические макро-периоды российской истории (`ERA_1`–`ERA_11`)

Эпохи определены в `public/data/sync.manifest.json` и вычисляются автоматически по годам событий (текущую наполненность по эпохам смотрите в разделе 4 файла `BRANCH_CATALOG.md`):

## 7. Стратегии генерации нескольких связанных веток

Когда новая тема состоит из двух и более связанных модулей (например, **«Русские писатели (годы жизни)»** + **«Их ключевые произведения»**, или **«Учёные»** + **«Открытия»**), используйте одну из двух стратегий:

### 7.1. Пакетная генерация (все файлы в одном ответе ИИ)
Подходит, когда вы сразу хотите получить 2+ взаимоувязанных JSON-файла (например, `public/data/writers_bio.json` и `public/data/writers_works.json`):
1. **Единые канонические теги:** для каждого писателя используйте строго `person-<surname>-<name>` (например, `"person-pushkin-alexander"`, `"person-tolstoy-leo"`, `"person-dostoevsky-fyodor"`). В файле биографий этот тег ставится в `syncTags` на узел писателя, а в файле произведений — в `syncTags` (для прижизненных работ) и/или в `referenceTags` (для посмертных изданий и книг о более ранних событиях).
2. **Связи через 3+ года и посмертные/ретроспективные книги:** если произведение написано позже жизни автора или описывает историческое событие спустя 50+ лет (например, роман 1971 г. о Первой мировой войне `1914-ww1`), используйте `"referenceTags": ["event-1914-ww1", "ww1", "person-solzhenitsyn-alexander"]` и/или явный `"linksTo"` с `"type": "references"`.
3. **Общая родительская группа (`isGroup`) без дублирования:** если хотите объединять связанные ветки в одну сворачиваемую группу на таймлайне (например, `LITERATURE_ALL`), объявляйте ветку с `"isGroup": true` **только в одном файле** (например, в файле биографий), а во втором файле укажите только `"parentBranchId": "LITERATURE_ALL"`. Объявление одинакового `branch.id` в двух файлах вызовет ошибку уникальности в `validate:branches`.
4. **Защита от визуальной перегрузки (длинные пересекающиеся биографии):** если в ветке десятки длительных интервалов (по 40–80 лет жизни одновременно), движок разведёт их в множество параллельных под-нитей (`subLanes`). Для таких справочных веток рекомендуется задавать `"defaultEnabled": false` (включается пользователем в меню фильтров) или объединять их под общей группой с `"defaultCollapsedOnTimeline": true`.
5. **Связь с историческими событиями базы:** используйте `"referenceTags": ["event-<node.id>"]` для отложенных отсылок (50+ лет) или существующие теги из `BRANCH_CATALOG.md` (`northern-war`, `napoleonic`, `ww1`, `ww2`) в `syncTags` (для событий той же эпохи) и `referenceTags` (для поздних книг/исследований).

### 7.2. Последовательная генерация (файл за файлом)
Подходит, если вы добавляете ветки поэтапно (сегодня — писатели, через неделю — произведения или театр):
1. **Шаг 1 (Первый файл):** передайте ИИ `BRANCH_SPEC.md` + текущий `BRANCH_CATALOG.md` и попросите сгенерировать первый модуль (например, `public/data/writers_bio.json`) с обязательными каноническими `syncTags` формата `"person-<surname>-<name>"`.
2. **Шаг 2 (Обновление каталога):** сохраните первый файл в `public/data/` и выполните `npm run sync:catalog` (или сделайте `git push` — GitHub Actions автоматически обновит `BRANCH_CATALOG.md`). В каталоге сразу появятся ID новой ветки, новые `syncTags`/`referenceTags` и точные `node.id`.
3. **Шаг 3 (Второй и следующие файлы):** передайте ИИ `BRANCH_SPEC.md` + **обновлённый `BRANCH_CATALOG.md`**. Модель увидит реальные `node.id` и теги первого файла и сможет поставить безошибочные `linksTo` (включая `"type": "references"`) и парные `syncTags`/`referenceTags` без догадок.

## 9. Команды валидации и автосинхронизации каталога

После добавления, изменения или удаления файлов веток в `public/data/` используйте встроенные npm-скрипты:

```bash
# 1. Проверить валидность всех JSON-веток, уникальность ID, формат тегов и ссылки
npm run validate:branches

# Жёсткий режим (ошибки даже на висячих ссылках и предупреждениях):
npm run validate:branches -- --strict

# 2. Перегенерировать BRANCH_CATALOG.md по текущим файлам в public/data/
npm run sync:catalog

# 3. Проверить без записи, что BRANCH_CATALOG.md актуален:
npm run sync:catalog:check
```

**Автоматизация в GitHub (`.github/workflows/sync-branch-catalog.yml`):**
- Срабатывает при добавлении, изменении или удалении **одного или сразу нескольких** `.json`-файлов в `public/data/**`.
- При `push` в `main`/`master`: запускает `npm run validate:branches`, пересобирает `BRANCH_CATALOG.md` (учитывая все новые ветки, узлы, `syncTags` и `referenceTags`) и автоматически коммитит обновление от имени `github-actions[bot]` с меткой `[skip ci]`.
- При `pull_request`: валидирует JSON-модули и фиксирует в summary статус обновления `BRANCH_CATALOG.md` (сам каталог обновится автоматически после мержа в `main`/`master`).
- **Важно для настройки репозитория GitHub:** в настройках репозитория (*Settings → Actions → General → Workflow permissions*) должно быть включено право **Read and write permissions**, чтобы бот мог пушить обновлённый `BRANCH_CATALOG.md`.

**Что проверяет валидатор (`validate:branches`):**
- Синтаксическую валидность всех `.json` в `public/data/`.
- Обязательные поля `fileId`, `branch`/`branches`, `nodes`, `task`, `period`, `title`, `subtitle`, `details`.
- Уникальность всех `branch.id`, `node.id` и `ruler.id` между всеми файлами.
- Корректность числовых лет (`startYear <= endYear`), формата ISO-дат (`YYYY`, `YYYY-MM`, `YYYY-MM-DD`) и строгого `kebab-case` формата тегов (`syncTags`, `referenceTags`, `campaignId`).
- Отсутствие циклических зависимостей `parentBranchId` и привязок узлов к веткам-группам (`isGroup: true`).
- Предупреждения о висячих ссылках (`linksTo` / `crossLinks`) и сводку активных тегов.

## 10. Готовый системный промпт для ИИ-моделей

Скопируйте текст ниже в System Prompt любой ИИ-модели **и приложите к запросу содержимое [`BRANCH_CATALOG.md`](./BRANCH_CATALOG.md)**, чтобы модель видела актуальные ID веток, теги и события в базе:

```text
Ты — историк-архитектор данных для модульного Git-таймлайна истории России.
Твоя задача — сгенерировать строго валидный JSON-файл новой ветки (или пакет взаимоувязанных JSON-файлов) для размещения в папке `public/data/<file_name>.json` без изменения кода сайта и без правки `sync.manifest.json`.
Опирайся на актуальный реестр веток, активных тегов и node.id из приложенного BRANCH_CATALOG.md.

ТРЕБОВАНИЯ К ФОРМАТУ:
1. Выводи ТОЛЬКО чистый валидный JSON-объект (если генерируется 1 файл) или чётко подписанные JSON-блоки с именами файлов `public/data/<file_name>.json` (если генерируется пакет из нескольких файлов), без лишних пояснений вокруг.
2. Корневая структура каждого файла:
   - "$schema": "https://git-timeline.schema.org/v2/branch.json"
   - "fileId": уникальный идентификатор файла в snake_case
   - "path": "data/<file_name>.json"
   - "version": "1.0.0"
   - "enabled": true
   - "branch" (для одной ветки) ИЛИ "branches" (для иерархии: родитель с "isGroup": true и дочерние ветки с "parentBranchId")
   - "nodes": массив событий, строго отсортированный по возрастанию startYear
   - "crossLinks" (опционально): явные связи между событиями

3. ПРАВИЛА ДЛЯ ВЕТОК (BranchDefinition):
   - Обязательные поля: "id" (UPPER_SNAKE_CASE), "gitName" (напр. "feat/..." или "war/..."), "label", "short" (<= 16 симв.), "description", "color" (HEX, НЕ используй #cbd5e1 и #f59e0b), "badgeClass", "isMilitary" (boolean), "category" ("military" | "economy" | "world" | "other").
   - НЕ используй id веток, уже занятые в BRANCH_CATALOG.md, и зарезервированные id: "MAIN_RULERS", "TIME_AXIS".
   - Чтобы подключить новую под-ветку в существующую группу (напр. "WAR_ALL"), задай "parentBranchId": "<ID_ГРУППЫ>".
   - Если создаёшь общую группу ("isGroup": true) для нескольких файлов в пакете, объявляй её ТОЛЬКО в одном файле; во втором файле указывай лишь "parentBranchId".
   - Для плотных/длинных фоновых веток (напр. биографии, книги, десятки длительных пересечений) устанавливай "defaultEnabled": false или оборачивай их в группу с "defaultCollapsedOnTimeline": true.
   - НИКОГДА не привязывай события (node.task) к ветке с "isGroup": true.

4. ПРАВИЛА ДЛЯ УЗЛОВ (TimelineNode):
   - Обязательные поля: "id" ("<YYYY>-<kebab-slug>", глобально уникален и не конфликтует с BRANCH_CATALOG.md), "startYear" (int), "endYear" (int, >= startYear), "period" (строка), "title", "subtitle", "details", "task" (id листовой ветки), "region", "type".
   - Если известны месяц или день, обязательно добавь "startDate" и "endDate" в формате "YYYY-MM" или "YYYY-MM-DD" для точного отображения на оси времени.
   - Для одномоментного события задай "startYear === endYear" и "isAtomic": true.
   - НЕ дублируй события смены правителей (они подгружаются из rulers.json автоматически).
   - Для детализации этапов добавляй "subEvents": [{ "title": "...", "text": "..." }].

5. ЕДИНЫЙ СТАНДАРТ ТЕГОВ (СТРОГО ASCII kebab-case: ^[a-z0-9]+(?:-[a-z0-9]+)*$):
   - Для каждого ПЕРСОНАЖА / АВТОРА: строго "person-<surname>-<name>" латиницей в именительном падеже без отчества (напр. "person-pushkin-alexander", "person-tolstoy-leo", "person-peter-1").
   - Для каждого СОБЫТИЯ базы: строго "event-<node.id>" (напр. "event-1914-ww1", "event-1812-patriotic-war") И/ИЛИ существующий тег кампании из BRANCH_CATALOG.md ("northern-war", "napoleonic", "ww1", "ww2").
   - Для сквозной ТЕМЫ: строго "topic-<slug>" (напр. "topic-silver-age", "topic-space-race").
   - НИКОГДА не придумывай произвольные варианты вроде "tolstoy", "l-tolstoy", "writer-pushkin" — придерживайся единой схемы префиксов person- / event- / topic-.

6. ПРАВИЛА СИНХРОНИЗАЦИИ (Синхронные связи и Отложенные отсылки через 50+ лет):
   - Слой 1 (прямые связи "linksTo"):
     * Для причинно-следственных и синхронных связей: "type": "triggers" | "enables" | "sync_context".
     * Для книг, фильмов, исследований и воспоминаний о прошлых событиях (даже через 50–200 лет): "type": "references" | "about_event" | "inspired_by", указывая "targetId" из BRANCH_CATALOG.md.
   - Слой 2 ("syncTags"): синхронная авто-связь между ветками в окне ±3 года (переиспользуй теги из BRANCH_CATALOG.md или ставь "person-<surname>-<name>" на биографию и прижизненные события).
   - Слой 3 ("referenceTags"): внеоконная авто-связь БЕЗ ОГРАНИЧЕНИЯ ПО ГОДАМ (через 5, 50, 100+ лет!). Ставь на книгу/исследование/позднее произведение:
     * "referenceTags": ["event-1914-ww1", "ww1"] — и книга автоматически появится в карточке события 1914-ww1 в разделе «Отражение в книгах, произведениях и отложенных событиях».
   - Удаление или отсутствие целевого файла не ломает сайт: все внешние ссылки безопасно изолируются.

7. СОДЕРЖАНИЕ:
   - Все тексты на русском языке, без HTML/Markdown внутри JSON-строк, исторически достоверно и лаконично.
   - Покрытие периодов ERA_1 (до 1223) — ERA_11 (1992–2000) работает автоматически без дополнительных настроек.
```
